# Decision 25

**Rule:** JSON matches the json gem: escapes, floats, generator options, `max_nesting`; parse keeps key order in `Hash`; 64-bit overflow raises `RangeError`.

JSON matches the json gem: escapes (quotes, backslash, control
characters; `/` and non-ASCII as-is) and floats (its `fpconv` rules,
e.g. `1e+20`, `0.0000123`) are ported.
`to_json(opts)` and `JSON.generate(obj, opts)` take the generator
options `indent`, `space`, `space_before`, `object_nl`, `array_nl`,
`depth`, `script_safe` (`escape_slash`), `ascii_only` and
`allow_nan`; `sort_keys`, `strict` and `as_json` raise
`NotImplementedError`, other keys are ignored as the gem ignores
unknown ones, and `max_nesting` is checked (see the amendment below). `JSON.pretty_generate`
is `generate` with the gem's `PRETTY_STATE_PROTOTYPE` (two-space
indent, one value per line) and `JSON.dump` is `generate`. Like the
gem, the generator calls every value's `to_json` with one (opaque)
state argument: a user `to_json` declared other than
`(*untyped) -> String` is reached through its dynamic wrapper, so
`(?untyped)` gets the state and `()` raises `ArgumentError`.
*(Revised: options were ignored, and such a `to_json` was skipped
for the JSON of its `to_s`.)*

`JSON.parse`/`.load` walk the token stream directly (not
`json.Unmarshal` into a Go map) so object keys keep insertion order
in rugaroo's `Hash`: an object becomes `Hash[String, untyped]`
(`Hash[Symbol, untyped]` with `symbolize_names: true`, keys chosen
once for the whole document), an array `Array[untyped]`, and
string/true/false/null map to themselves. Numbers are decoded with
`json.Decoder.UseNumber`, so a literal with no `.`/`e`/`E` is
Integer and any other is Float, as the gem. A duplicate object key
keeps its first position and takes the last value, as Ruby Hash
assignment. An integer literal that does not fit in 64 bits raises
`RangeError` rather than the gem's Bignum (decision 35: no Bignum),
matching `String#to_i`'s and a literal's own overflow. Malformed
input raises `JSON::ParserError`; message text is Go's decode error,
not ported from the gem's parser. `JSON.load` is `.parse`: the
gem's docs call `.load` unsafe for arbitrary Ruby objects, but
rugaroo's closed, untyped-only world has no such objects to inject.
*Amended (#101, security):* `max_nesting` is checked, as the gem does.
Parse (`JSON.parse`, `.load`) and generate (`to_json`, `generate`,
`pretty_generate`) default to 100, and `JSON.dump` to unlimited; the
`max_nesting:` option takes an Integer (Float truncates),
`false`/`nil`/`0` turn the limit off, and any other value raises
`TypeError`. A container deeper than the limit raises
`JSON::NestingError` (< `JSON::ParserError`; MRI raises it on the
generator side too). The parser reports the depth reached ("nesting
of 101 is too deep") and does not count empty containers. The
generator counts every container, empty ones too, reports "nesting
of 100 is too deep. Did you try to serialize objects with circular
references?", and shares one state across nested `to_json`, so a
cycle ends in `NestingError`. A hard cap of 10000 applies even when
the option is off, because a Go stack overflow is fatal and `rescue`
cannot catch it (MRI raises a catchable `SystemStackError`, or parses
without recursion). Go's own `json.Decoder` stops at 10000 as well, so
the parse-side cap only keeps the error class consistent.
*See also decision 271:* `JSON.dump(obj, io)`, `freeze: true` and the
other parse options. *See also decision 346:* the generator no longer
calls `to_json` on a plain String, Integer, Float, true/false/nil, Array
or Hash, as the gem 2.x does not.
