# Decision 350

**Rule:** Hash is an insertion-ordered entry array plus key index (tombstones, no map up to 8 entries); `h[k] op= v` on scalar V updates in place.

**Hash is an entry array plus a key index; `h[k] op= v` updates in place** (amends 1, 236, 342, 344; 2026-10-23). *See also decisions 1, 5, 342, 344, 388* (`pos` is now an open-addressed `slots []int32`). Hash was `keys []K` plus `vals map[K]V`: iterating did a map lookup per key, `delete` scanned and shifted the key list (O(n)), and `h[k] = h[k] + 1` hashed the key twice.
- **Layout.** `ents []rbHashEnt[K, V]` (key, value) in insertion order, `pos map[K]int32` from each live key to its entry, `live` (the size), and tombstones as a bitmap (`gone []uint64`, allocated by the first delete), not a per-entry flag, so an Integer=>Integer entry stays 16 bytes. Iteration walks `ents` skipping tombstones (no lookup); `[]=` on a present key writes its entry (position kept); a new key appends (a deleted key re-inserted goes last, as MRI's); `delete` drops the key from `pos` and tombstones the entry. The eql?-by-value index (`rbKeyIndex`) is unchanged: it still maps a key to its canonical stored key, which `pos` then finds.
- **Compaction never runs while an iterator is open** (`iter > 0`, MRI's iter_lev), so an index an iterator holds stays valid: a delete during `each` only tombstones, and `clear` during `each` tombstones every entry in place. With no iterator open, a delete that leaves the Hash empty resets it (storage kept), and one that leaves more than half of 16+ entries dead compacts and renumbers `pos`; `delete_if`/`keep_if` compact once at the end. `[]=` never compacts. `shift` takes the first live entry from `head` (advanced past leading tombstones), so a queue of shift + push is amortized O(1).
- **Small Hashes have no map.** Up to 8 entries (`rbSmallHash`) `pos` is nil and a lookup scans `ents` with `==`; the 9th entry builds `pos`. Most Hashes (options, JSON objects, liquid's contexts) stay that small, and a scan of a few keys costs less than hashing one, and saves the map's allocation. A NaN key never matches by `==` in either mode, as before (each `h[nan] = v` adds an entry); it now also iterates, where the old layout's per-key lookup skipped it.
- **Compile cost.** The new helpers are free generic functions, not methods, so an instantiation compiles only those it calls (Go compiles every method of an instantiated type); the tombstone test (`rbGone`) is not generic at all; the scan is written out in `rbGet`, `[]=` and `delete` rather than shared; the Go helpers that loop over a Hash use `rbHashPairs` (range-over-func) but the per-instantiation Hash methods use plain index loops, whose closures would otherwise be compiled per instantiation. The untyped view's `_KeyAt(i)`/`_PairAt(i)` became `_KeysAny()`/`_PairsAny()` (decision 236): with tombstones an insertion index is not a slot.
- **Fused read-modify-write** (`expr_hashfuse.go`). `h[k] op= v` and the literal shape `h[k] = (h[k] || d) op v` on the prelude's own `Hash` (not a subclass or a reopened `[]`/`[]=`) with an Integer, Float or String V compile to `if p := rbHashSlot(h, k); p != nil { r = *p op v; h.rbCheckFrozen(); *p = r } else { <the unfused code> }`: a hit hashes k once and keeps decision 35's overflow check (the operator call is the same `Integer.Op_plus`); the frozen check comes after the new value is computed, as `[]=` runs after it in Ruby. A miss runs the unfused code unchanged, so the default value or proc, insertion order and the during-iteration RuntimeError behave as before; no run-time default-proc test is needed, because a present key never reaches the default. It fuses only when nothing between the lookup and the store can run Ruby code that touches the Hash (the slot is a pointer into `ents`, valid until the next append): op is `+ - * / %` (String: `+`), the result type is V, and v is a literal, local, ivar or constant, or such operands combined by those operators on Integer/Float (an Integer's `+` with another class would call its `coerce`). The `=` shape also needs h to be a local or ivar and both `k`s the same pure source text, since Ruby evaluates k twice and the fused form once.
- Not fused: `h[k] ||= v` (a hit already is one lookup; a miss must insert anyway), `&&=`, receivers that are method calls in the `=` shape, other operators (`<<` on a String mutates in place, `**` can change type), and V of any other class (a user `+` could mutate the Hash).
- Measured (instructions retired, `GOMAXPROCS=1`, median of 5; base, layout, layout + fusion, M): hash 173 / 168 / 96; json 2,287 / 2,021 / 2,005; kramdown 4,604 / 4,427 / 4,360; liquid 2,130 / 2,085 / 2,087; blocks and collections vary ±5% between runs (GC timing), so their medians of 15: blocks 1,057 / 1,025 / 1,017, collections 1,932 base to 1,902 with both steps; the other nine within ±0.7%. An insert-heavy program (five 400k-key Hashes kept live, plus 200k 3-key Hashes) used 169 MB before and 171 MB after, with 19% fewer instructions; one that also deletes 20k keys from each 200k-key Hash went from 136G instructions to 3.4G (O(n) delete). Compile cost (TestCompileCost, compiled functions): 05_word_count 1,938 to 1,941, 64_observable 7,596 to 7,618, 116_cuba_web 29,645 to 29,766 (+0.4%: the tombstone compaction and delete helpers each instantiation that deletes now compiles).
- **Proof:** `hash_test.rb` `HashLayoutTest` (re-insert order, 100-key delete and compaction, delete/clear/shift during `each`, new key during `each`/`delete_if`, shift as a queue, frozen mutators, eql? keys after delete, dup/merge/== after deletes) and `HashFusedTest` (op-write and `= (h[k] || d) op v` values, Float/String/`%`, an ivar Hash, default value and default proc on a miss, ZeroDivisionError and FrozenError leaving the entry, updates and a new key during `each`), against MRI.
