# Decision 329

**Fast Fiddle calls** (#32; amends 96, 326, 327; 2026-10-20). Measured with sqlite3-fiddle's `bench/benchmark.rb` (100k-row insert in a transaction, `execute` of every row, the same as hashes, 20k primary-key lookups, a Ruby SQL function over 100k rows), seconds, best of 3 on an Apple M4, against MRI 4.0.7 with the sqlite3 2.10.1 C extension:

| | insert | select | select_hash | point_lookup | ruby_function |
| --- | ---: | ---: | ---: | ---: | ---: |
| MRI + C extension | 0.161 | 0.049 | 0.097 | 0.031 | 0.013 |
| rb2go before | 1.294 | 2.090 | 2.861 | 0.628 | 0.671 |
| rb2go after | 0.149 | 0.203 | 0.290 | 0.049 | 0.096 |

Every change is in the Fiddle layer or the runtime, so any Fiddle program gets it; the gem changed one line (`bind_param` asks for the database handle only when the bind failed, since the handle only feeds the error message). Each change was measured on its own and kept only if it helped.
- **No reflect per call.** `purego.RegisterFunc` binds through `reflect.MakeFunc`: for decision 326's 16-register superset signature that was ~900 ns and 18 allocations per call. `rbFiddleCall` now fills purego's own argument block (purego's `syscallArgs`, mirrored as `rbFiddleArgs`) and runs purego's assembly trampoline through `runtime.cgocall`, both reached with `//go:linkname` (purego links `runtime.cgocall` the same way, and a bodyless linknamed func needs no `.s` file, so `rb2go gen` still emits one `main.go`): ~80 ns, no allocation, floats included. The block is heap memory, not the stack, since a callback into Go during the call may move the goroutine's stack; each prepared function keeps one, taken with an atomic swap (a concurrent call on another thread finds the slot empty and makes its own): a `sync.Pool` round trip cost a third of the call. A cgo call to an empty C function is ~29 ns here; the rest of the ~46 ns is purego's trampoline, which loads all 32 argument slots and, on darwin, calls `__error`. On darwin the trampoline itself reads errno; elsewhere a second call to `__errno_location` does, on the same locked OS thread. The layout is purego v0.11.2's 64-bit one; a purego bump re-checks it. libc `malloc`/`free`/`realloc` go the same way.
- **Extern methods skip `Function#call`'s `*args`.** A synthesized `extern` method (326) is now `::Fiddle.__call2(__fiddle_func_at(k, "name"), a0, a1)` (`__call1`..`__call3`, then `__call(f, n, a0, ..., a7)` up to 8 arguments): fixed parameters, so no Array per call. `rbFiddleFast` converts Integer, Float, String, true/false, nil and a plain `Fiddle::Pointer` in Go and answers `f` itself (never a C result) otherwise, and then `f.call` runs as before: for a Function subclass, which may override `call`, or for any other object. `Function#call`'s own argument conversion moved to Go as well. A String passed as a pointer is copied into Go memory kept alive across the call instead of `malloc`/`free`d (still C memory, leaked, when the result is a `void *` that may point into it).
- **`__fiddle_func_at(k, name)`** reads the Function from an Array slot the compiler numbered per module, not by hashing the name on every call; `extern` and `bind` empty that cache, so a redefined name is seen, as MRI's `@func_map` lookup sees it.
- **`Fiddle.last_error`** is stored from Go into the thread-local MRI uses. The Thread's `fiddleErrno` field remembers the errno the last call stored (`Thread#[]=` forgets it), so an unchanged errno costs one atomic load instead of a `sync.Map` store.
- **Callbacks without reflect.** purego calls every callback through its package variable `callbackWrap_call`, which reads each parameter through reflect (~1 µs for the superset signature). rb2go puts its own function in that variable (linkname, once): for a closure rb2go registered whose arguments all fit in registers (8 integer on arm64, 6 on amd64, and 8 floating), it reads them from purego's saved-register frame and calls the block directly (~300 ns per callback including the block, against ~1.5 µs); any other callback index, or one with stack arguments, goes on to purego's. Other architectures keep purego's path (ponytail).
- **`String#freeze`** (amends 96). The 256 copy-on-write shards copied about n/256 entries per freeze (quadratic over a program) and kept every frozen string alive. Now the 256 shards are plain maps, each behind its own mutex held for a map operation (no process-wide lock, decision 147), keyed by address and length. A freeze records the string itself; a goroutine (`rbFrozenConvert`, woken every 256 freezes) replaces such entries with a `weak.Pointer` to the bytes, off the freezing thread, so a string is pinned only until then. An entry whose bytes died reads as unfrozen, so a new string at a reused address is not frozen, and a shard rebuilds itself without its dead entries when it doubles (deleting in place left tombstones that lengthened every probe). Bytes in Go's read-only data (strconv's digits, one-byte strings), on which `weak.Make` is fatal, are immortal entries, found by the linker's `runtime.rodata`/`runtime.erodata` bounds. A `sync.Map` was tried and cost twice `weak.Make` itself. `weak.Make` (~400 ns) is the floor of any set that learns when a string died: Strings are values (136), so there is no object header for MRI's flag bit. A freeze now costs its caller ~300 ns (a map insert into a set that holds every live frozen string, so mostly cache misses), against ~900 ns before.
- **Smaller wins.** `Encoding.find(an Encoding)` returns it (it compared every encoding's names, so `force_encoding(Encoding::UTF_8)` paid that per column). `Hash#rbFrom` (the copy that turns e.g. `zip(...).to_h`'s `Hash[String, untyped?]` into a declared `Hash[String, untyped]`) reads the pairs directly instead of through a `Hash[any, any]` copy with its own key index.
- **What is left.** insert and point_lookup are within 2x of the C extension. The other three cross C ten times a row (step, column count, type and value per column) or three times per callback, as the C extension does, but each crossing is a `runtime.cgocall` (~80 ns: the switch to the system stack and the scheduler hand-off that lets a long C call block) where the C extension pays a few ns. The same select made from Go through the same trampoline and argument block, with no Ruby at all, takes 0.082 s, 1.7x the C extension. Of rb2go's 0.203 s, 0.082 is that floor, ~0.03 is `String#freeze` (the gem freezes each TEXT value, as the C extension does), ~0.06 is the Ruby-to-Fiddle layer per call (boxing the untyped arguments and the result, the Function lookup, `last_error`), and the rest builds rows. So the remaining gap is not only the C call: closing it needs the arguments and results of an `extern` unboxed (typed by the C signature, where MRI accepts any Integer-like value) and a frozen flag that is not a side table, which Strings as values (136) do not have. ruby_function's time is all inside `sqlite3_step`: purego's callback entry plus three nested C calls per row.
- **Proof:** `testdata/test/fiddle_test.rb` gained a closure with double, int, float and long arguments called through a Function, one with seven integer arguments (past amd64's six registers), and `last_error` after `Fiddle.last_error =` and `Thread.current[...] =`; examples 121 and 122 and `sqlite3_test.rb` unchanged; the gem's own suite on MRI, against the C extension, on JRuby, and its shared test under rb2go on darwin and in a linux/arm64 container.
