# Decision 357

**Rule:** A `T?` local that a statement or condition always calls a nil-raising method on reads as `T` after it, and a branch that reassigns a narrowed local and narrows it again keeps the outer narrowing.

**Narrowing that survives a call, and a branch's re-narrowing** (amends 14 and 20; 2026-10-23). *See also decisions 14, 20, 148.* `benchmarks/splay.rb` (spinel's, unmodified) walks a tree with `sl = dummy; sr = dummy; t = @root` and then `if key < t.key ... sr.left = t; sr = t; t = t.left`. `t` is `SplayNode?`, `sr` is `SplayNode`, and decision 20 keeps a `T?` into a `T` local a compile error ("possibly-nil SplayNode? where SplayNode is expected"). Widening `sr` to `SplayNode?` was rejected: it is the error decision 20 chose, and it would make every `sr.left = t` a nil-checked call.
- **A call that raises on nil narrows its receiver.** `t.key` on a `t` of type `T?` compiles to a nil check that raises NoMethodError (decision 20's `nilGuard`), so code after it runs only when `t` is not nil, in MRI as here. After a statement, a `T?` local that the statement always called such a method on reads as `T` for the rest of the scope (`callNarrowing`, `gen_cond.go`), and an `if`/`unless` condition's calls narrow both branches and what follows. Always: the receiver chain and arguments of calls, the left of `&&`/`||`, an `if`'s condition, an assignment's value, `return`'s arguments; not branches, the right of `&&`/`||`, blocks, `&.` or calls nil answers (`to_s`, `nil?`, `==`, decision 20's list), which do not go through `nilGuard`. Not a local the statement itself writes (`t = t.left`) or that any block of the method writes. binary_trees' `node.left == nil` narrows `node` the same way.
- **A branch's re-narrowing restores the outer one.** `y = t.left; ... t = y; if t.left.nil? break end` inside an `if`: the write drops `t`'s narrowed view in every enclosing scope (`unnarrow`), and the guard re-narrowed it only in the branch, so `sr = t` after the `if` failed. `unnarrow` now records each enclosing view it drops on the innermost scope (`killedView`); when an `if`/`unless` branch ends (`leaveBranch`) with the local narrowed to the same type again, its last statement's guard included, or never falls through, the view is put back. Records a branch cannot restore pass up to the enclosing scope, so an outer branch that re-narrows later can. A branch that can `break`/`next`/`redo`/`retry` restores only views inside the innermost loop (the jump reaches code past the loop, where the local may still be nil); a block's records are dropped (a block runs later). A guard after a write in a branch also finds the local when it is hoisted, whose view the write removed from scope (`narrowLocal`): `l = t.left; break if l.nil?; if c; t = l; l = t.left; break if l.nil?; end; t = l` failed at `t = l`.
- **Proof:** `testdata/test/infer_test.rb` `RecTree#leftmost` (the guard-after-write shape) and `#add`, `count_tree` (`node.left.nil?`), `TestSpinelBenchmarksTyped`; splay: 0 `rbDyn` and no dynamic-call warning (was 5 dispatchers, 35 warnings); TestCompileCost compiled functions unchanged (1,942 / 7,624 / 29,782).
- **Not done:** a `while`/`until` condition's calls do not narrow the loop body; a ternary's `x.nil? ? a : x.foo` still does not narrow (decision 148).

See also decision 371: the same narrowing applies between the operands of `&&`/`||`.
