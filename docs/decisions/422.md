# Decision 422

**Rule:** An instance variable that user code reads and nothing assigns stays a compile error ("has no known type"), as user code stays strict, while one only ever assigned nil is untyped with a warning (decision 183); and cmd/rubyspec's mock of a stubbed setter is a `def ... end` that takes its value.

**Bundled-gem backfill, twelfth batch: net-ftp's remaining buckets, one by one** (2026-10-30). *See also decisions 179, 183, 416, 421.*

A review asked for net-ftp's errors and skips mapped individually rather than by decision 416's summary. Doing so found one harness bug, one misattribution, and the exact cause of the largest bucket.

- **A stubbed setter's mock did not parse.** `@socket.stub!(:read_timeout=).and_return(3)` (close_spec) made cmd/rubyspec's mock class (decision 179) emit `def read_timeout=() = 3`; Ruby has no endless setter, so the whole `RbSpecMock1` dropped and all three examples errored with `uninitialized constant RbSpecMock1`. A setter (`name=`, not an operator) is now `def read_timeout=(_value)` with the body on its own line. `does not try to close the socket if it is nil` passes; the other two use `should_receive` on the mock (mspec message expectations, decision 416). `library/net-ftp` 331 → 332 of 460.
- **The largest bucket is one user-code rule, not "ivars only ever nil".** net-ftp's shared specs set up with `@ftp.binary = @binary_mode`, a mode only an including spec would set and these never do; MRI reads nil. rugaroo compiles spec code as user code, and a read of an ivar nothing assigns is a compile error there: `testdata/errors/objects.txtar`'s `ivar_never_assigned`, `attr_without_type` and `ivar_in_class_method_untyped` pin it. With the shared `before` block's first statement refused, cmd/rubyspec's per-example isolation drops the block, and the ivars only it writes (`@ftp`, `@remote_tmp_file`) lose their writes too: 59 + 7 + 7 skips, plus initialize_spec's 40, whose `@ftp = Net::FTP.allocate; @ftp.stub!(:connect)` falls to mspec's partial mocks. Decision 416 attributed the bucket to decision 183; 183 relaxes only an ivar assigned nil, and its Rule line, which said "ivar nothing in the program types", now says so.
- **Why it is kept.** Declaring a never-assigned ivar untyped (a warning, as for an only-nil one) was measured: `library/net-ftp` went to 405 of 460. It was not adopted: in user code an ivar nothing writes is almost always a typo or a missing assignment, which the compile error names, and the goal of this backfill keeps user code strict. Gem code already declares such ivars untyped (decision 220). Policy (the user, 2026-10-30): only a real program justifies loosening user code, as an opt-in flag in the manner of decision 393; ruby/spec numbers never do. The measured change is parked in issue #146.

**Every non-passing example left in `library/net-ftp` (332 of 460), by cause:**
- A read of an ivar nothing assigns, in spec code (this decision): 73 skips (`@binary_mode` 59, and the `@ftp`/`@remote_tmp_file` writes its setup takes down, 7 + 7).
- mspec's partial mocks and message expectations (decision 416): 47 skips (`stub!` on a spec object or a real one, initialize_spec's 40 among them), 2 skips and 1 error (`should_receive` on a mock or on Net::FTP), 3 skips in open_spec (`should_receive`/`stub!` on Net::FTP and its class).
