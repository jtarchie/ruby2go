# Decision 403

**Rule:** A goroutine that runs Ruby takes its id from an atomic counter and a Thread records its creation stack unresolved; a Fiber is an `iter.Pull` coroutine whose goroutine tag carries it; `SizedQueue` is a Go channel swapped whole by `max=`; `Kernel#rand` and `Random.rand` draw from `math/rand/v2` unless the pruned program reaches `srand`, in which case they keep the shared, locked MT19937.

**Concurrency on Go's own primitives** (amends 45, 104, 140; 2026-10-27; #142). *See also decisions 26, 49, 60, 147, 332.*

Measured against MRI and spinel (matz/spinel `baea3e28`, its own M:N green-thread scheduler, also without a GVL), rugaroo won where parallel CPU work or the garbage collector was the cost and lost where the cost was a handoff between goroutines. Each fix below uses goroutines, channels, `sync`, `sync/atomic` or another standard package as it comes; none is a hand-written lock or scheduler.

- **Thread and fiber start.** `rbTagGoroutine` gave each new goroutine its id by parsing `runtime.Stack` (decision 104), and `rbThreadStart` resolved the creator's `file:line` for `Thread#inspect` on every start (`rbCallerLoc`: a frame walk and string trimming). The id is now `rbGoCounter.Add(1) + 1<<40`, clear of the goroutine numbers `rbGoIDStack` still parses for main and for an untagged goroutine, and a Thread keeps the raw `runtime.Callers` program counters (`rbCallerFrames`) that `inspect` resolves when it prints. Main keeps its parsed id, so every `rbMainGoID` comparison holds.
- **Fiber.** A fiber was a goroutine handed control over two unbuffered channels (decision 140), two channel operations a direction. It is now `iter.Pull` over its body, as Enumerator's `next` already was: `resume(*args)` stores the packed arguments and calls `next()`, `Fiber.yield(*vals)` calls the body's `yield` and reads the arguments the next resume stored. An exception in the body is kept and raised by the resume that sees the coroutine end. The coroutine's goroutine does not inherit pprof labels, so the body tags itself first, and the tag (`rbGoTag.fiber`) answers `Fiber.current` and `Fiber.yield` without a map lookup per switch; `rbFiberOf` stays for catch/throw's tag list (decision 91). `iter.Pull`'s `next` works from any goroutine, so MRI's cross-thread resume check stays as not done.
- **SizedQueue.** A contended `sync.Mutex` around a tiny critical section costs about 170-195 ns a pair on 8 goroutines (starvation mode's direct handoff), whatever the code around it, so changes to `rbQueue`'s wake-ups measured as noise. A bounded queue is a Go channel, whose runtime lock is not a `sync.Mutex`: `rbBounded` pushes and pops on `chan E`, waits in a `select` with the queue's `done` (close), the current channel's `gen` (resize), a timer (`pop(timeout:)`) and, on main, the interrupt channel (decision 60). `close` never closes the channel, since a racing push would panic; it closes `done`, so a blocked push raises `ClosedQueueError` and a blocked pop takes what is left, then nil. `max=` raises `resizing`, closes the old channel's `gen`, waits out the pushes already past their `resizing` check (sequentially consistent atomics: either the push sees the flag or `max=` sees it in flight), moves the old items to a channel of the new capacity (or of the current length, if more are held), and publishes it; woken pushers and poppers wait for the resize's lock to drop before retrying, so no item is lost or reordered. An unbounded `Queue` has no channel equivalent and stays on `rbQueue` (decision 45).
- **`Kernel#rand`.** `rbDefaultRandom` is one MT19937 behind one mutex, which serialized every thread drawing from it: the one process-wide lock left on a hot path (decision 147). MRI's seeded sequence must hold (`srand(1); rand`), so the choice is the pruner's: `rbSrand`, which `Kernel#srand` and `Random.srand` call, names `rbRandSeededMark`, whose initializer sets `rbRandSeeded`. A program that can reach `srand` keeps the variable alive and draws `Kernel#rand(n)`, `rand(range)`, `rand` with no bound and `Random.rand` from the shared generator, as before; a program that cannot drops it, and draws from `math/rand/v2`'s top-level functions, which the Go runtime keeps per P without a lock. Nothing in such a program can depend on the sequence, which starts from a random seed. `Random.new(seed)`, `shuffle`, `sample` and `Random::DEFAULT`-style uses keep MT19937. `math/rand/v2` imports as `mrand` (`stdImportAlias` in `format.go`), beside `crypto/rand`.
- **Mutex** is unchanged. Dropping decision 104's owner tracking measured within noise; the cost is `sync.Mutex`'s handoff itself.

Measured on one 8-core Apple-silicon machine (load average about 3), median of 3, wall seconds and instructions retired:

| workload | before | after | spinel |
|---|---|---|---|
| 20k `Thread.new` + `value` | 0.12 s, 1.71G | 0.05 s, 0.49G | 0.07 s, 0.49G |
| `Fiber` resume/yield, 300k | 0.23 s, 1.64G | 0.07 s, 0.45G | 0.05 s, 0.29G |
| 8 threads x 1M `rand(1000)`, unseeded | 1.42 s, 8.48G | 0.01 s, 1.09G | 0.02 s, 0.79G |
| 4 producers, 4 consumers, 1M items, `SizedQueue.new(4096)` | 0.45 s (unbounded `Queue`) | 0.13 s | 0.11 s (`Queue`) |
| hot `Mutex`, 8 threads x 300k | 0.39 s | 0.35 s | 0.18 s |
