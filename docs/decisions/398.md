# Decision 398

**Rule:** A user or gem module's singleton class is a leaf (decision 359): its class methods take `self *M_Meta`, so a module ivar read is a field load, and a leaf's shared `-> self` dynamic wrapper (`dup`, `freeze`) needs no `rbPtrAny` box.

**Module metaclasses as leaves** (amends 359; 2026-10-27). *See also decisions 210, 359.* spinel's `bm_getivar_module` (`def self.get_value_loop` summing `@levar` 100M times) ran 1,619M instructions against `bm_getivar`'s 107M for a tenth of the work. The class version takes `self *TheClass` (359); the module version compiled to `func TheModule_Meta_GetValueLoop(self TheModule_MetaI)`, so every `@levar` was `self._TheModule_Meta().levar`, an interface call Go cannot inline or hoist. Decision 359 excluded every metaclass from `leaf()`.

- **Why a module's and not a class's.** Nothing can subclass a module, so its singleton class has exactly one Go type, `*M_Meta`. A class's metaclass does not: its subclasses' metaclasses inherit its class methods, and that hierarchy is recorded on the class (`metaOf.Subclasses`, walked by `callMethod`'s class-method dispatch), not on the metaclass, so `len(meta.Subclasses) == 0` says nothing. A class metaclass whose class has no subclass and no per-run `Class.new` could be a leaf too; not done (ponytail).
- **Guards kept.** `extend UserModule` lands in the metaclass's `Includes`, so `mixesUserModule` keeps such a module out, as for a class; `extend` of a prelude module is fine.
- **Synthesized methods.** A metaclass's `name`/`to_s`/`inspect` (`kindSynth`) are Go methods on `*M_Meta` with no free func; a leaf's call goes to the free func, so `staticCallCode` calls them as methods.
- **Shared wrappers.** A leaf's dynamic `dup`/`freeze` wrapper was `rbPtrAny[C](Kernel_Dup[*C](self))`, which named the class, so each leaf took its own `DynDup`/`DynFreeze` method instead of the shared `Kernel_Dup[any](self)` arm. `unboxLeafSelf` drops the box (self is never nil). It pays for the new leaves and trims 359's: TestCompileCost compiled functions 05_word_count 2,054 → 2,054, 64_observable 7,980 → 7,962, 116_cuba_web 30,466 → 30,311 (before the unbox: 30,541).
- **What spinel does.** Module ivars are C globals (`civ_TheModule_levar`); clang hoists the load and folds the checked adds, so its binary retires 14M instructions in all, its startup. rugaroo's loop is now ~8.8 instructions per checked add, the same as `bm_getivar`'s: Go does no loop-invariant code motion, so the field load and overflow check stay per add. Closing that would take our own hoisting of loop-invariant ivar reads, a separate pass not built here.
- **Measured** (instructions retired, M, GOMAXPROCS=1, paired alternating, median of 5, main bec61a55 → this): bm_getivar_module 1,619 → 899 (1.80x), bm_getivar 107 → 107. benchmarks/*.rb: only kramdown and liquid (traced gem modules) build to a different binary: kramdown 4,262 → 4,255, liquid 1,859 → 1,856; the other 16 are byte-identical binaries (their deltas, up to ±2.4% for json, are run-to-run noise). All print what they printed before.
- **Proof:** `ObjLeafModTest` in `testdata/test/object_test.rb` (module ivars read and written by class methods, a module as a `Module` value, `name`, `is_a?` through `extend`, `module_function`) against MRI; the suite.
